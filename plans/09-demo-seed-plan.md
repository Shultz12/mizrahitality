# Feature #9 — demo-seed

## Context

`scripts/seed.mjs` is still the feature-#1 no-op stub (`console.log('seed: nothing to do yet…')`), yet `pnpm seed` is wired and the README's setup flow already lists it between `pnpm db:migrate` and `pnpm dev` with the promise "populate demo data (Venue #1 history, Venue #2 empty)". This is the last feature in the build chain (`#1…#9`) and the enabler for the GA gate from the PRD — *"full reviewer walkthrough passes with no setup beyond running the seed"* and the success metric *"Reviewer can switch all visitor types → distinct variants, watch metrics move, see Venue #2 fill, with only the seed run"*.

The goal: turn `scripts/seed.mjs` into a one-command demo dataset — two owner accounts, each with a fully-built **published** venue ("Hotel Mizrahi" for Owner #1, "The Levant House" for Owner #2; name → derived slug, free-text description, a stock image, all 7 validated `PageVariant` copy bundles), where **Owner #1's** venue carries ~30 days of realistic historical analytics events (shaped so every dashboard figure / chart / percentage is non-trivial) and **Owner #2's** venue starts with zero events (so its dashboard shows the zeroed "No data yet" state and a reviewer can watch it fill by visiting its customer page). Re-running the seed resets the demo data cleanly. The script needs **no `ANTHROPIC_API_KEY`** (variant copy is committed canned JSON) and no schema change.

This is purely additive: **no Prisma migration / `CHANGELOG.md` entry, no `@mizrahitality/contracts` change, no new runtime deps** — `Owner` / `Venue` / `Session` / `PageVariant` / `Event` already have every field the seed writes (confirmed in `apps/owner/prisma/CHANGELOG.md` and the per-feature notes), and `bcryptjs` + `@prisma/client` are already `apps/owner` deps resolvable from the root script via the hoisted `node_modules` (`.npmrc` `node-linker=hoisted`).

## Decisions (resolved with the user)

1. **Variant copy = canned committed JSON.** The 7-per-venue `CopyBundle`s are committed under `scripts/seed-data/`. The seed reads them and writes each as `PageVariant.content = { schemaVersion: SLOT_SCHEMA_VERSION, copy: <bundle> }` — the exact wrapper `apps/owner/src/lib/page-variant.ts` `parsePageVariantContent` expects (and what `runPublishPipeline` writes). Generated **once** during implementation (publish each demo venue through the running owner app with `ANTHROPIC_API_KEY` set, against a scratch `dev.db`, then export the 7 `PageVariant.content` rows — or hand-author bundles that pass `validateCopyBundle`); thereafter the seed needs no API key, is offline, and is deterministic. Matches the charter's "prefer canned variant JSON checked in or generated once" and the GA "no setup beyond the seed" gate. (Slight drift risk: the canned `schemaVersion` is hardcoded `1`; a future `SLOT_SCHEMA_VERSION` bump would need the canned data + the seed updated — guarded by the new validation test below.)
2. **Owner #2 = a published venue with 0 events.** Owner #2 has its own fully-built, published venue ("The Levant House", slug `thelevanthouse`) with its own committed 7-bundle set and **zero** `Event` rows. Its `/dashboard` renders the zeroed "No analytics yet … No data yet" state (never an error — `computeDashboard([])` is a fully-formed zeroed object); its `:5112/thelevanthouse` page works, so a reviewer can visit it and watch the dashboard fill (no API key needed). Cost accepted: a second canned bundle set (14 bundles total).
3. **Re-run = reset the demo data, then recreate.** On every run, the seed first `prisma.owner.deleteMany({ where: { email: { in: [DEMO_OWNER_1_EMAIL, DEMO_OWNER_2_EMAIL] } } })` — cascade-removing each demo owner's venue → variants + events + sessions — then recreates everything fresh. Re-running `pnpm seed` is therefore a clean demo reset (documented). It never touches owners that aren't the two fixed demo emails.
4. **Demo venues:** Owner #1 → **"Hotel Mizrahi"** (slug `hotelmizrahi`); Owner #2 → **"The Levant House"** (slug `thelevanthouse`). (Names validate against the builder's `^[A-Za-z]+( [A-Za-z]+)*$` rule; slugs = `deriveSlugBase(name)` = lowercase, whitespace removed — no collisions in the seed.)

Decided in-plan (not blocking, see "Open questions to pin"):
- **Demo credentials:** Owner #1 = `owner@mizrahitality.test` / password `mizrahitality`; Owner #2 = `owner2@mizrahitality.test` / `mizrahitality`. (Passwords are stored via `bcrypt.hash(pw, 10)` — cost 10, matching `apps/owner/src/lib/auth.ts`'s `BCRYPT_COST`; sign-in doesn't re-validate password strength, so these short demo passwords work fine. The seed does **not** create `Session` rows — sessions live in a browser cookie; the reviewer signs in normally.)
- **Stock images:** "Hotel Mizrahi" → `imageKind:'stock', imageValue:'mardan-palace'`; "The Levant House" → `imageKind:'stock', imageValue:'burj-al-arab'` (both committed under `apps/owner/public/stock/`; ids from `apps/owner/src/lib/stock-images.ts`; `atlantis-paradise` is left unused).
- **Venue timestamps:** `publishState:'published'`, `publishedAt` and `slugLockedAt` set to ~31 days ago, `createdAt` ~32 days ago, so the venue "predates" its analytics history (coherent; Prisma lets `@default` fields be set explicitly on create).
- **Historical events (Owner #1 only):** ~30 calendar days ending today, bucketed in the **server's local timezone** (matching `computeDashboard`'s default `timeZone:'local'` — so the daily chart is always populated when you run the seed). Driven by a tiny **seeded PRNG** (e.g. `mulberry32` with a fixed constant) so the dataset is reproducible. Illustrative parameters (tunable — the only hard requirement is *every* dashboard figure is visibly non-trivial): daily visits ramp ≈ `10 + 2·dayIndex` ± ~20% noise (day 0 ≈ 10 → day 29 ≈ 68; ~1,100–1,200 total `visit` events with a clearly **upward** OLS trendline); per visit-session: assign a visitor type — ~8% `neutral`, otherwise gender 55% female / 45% male and age 30% `18-30` / 45% `31-50` / 25% `50+` (all 6 segments well-populated, neutral present); each session gets a `crypto.randomUUID()` `sessionId` shared by its events; it emits a `book-now-click` with a per-segment probability (≈ 5%–16%, distinct per segment so the conversion table varies — e.g. `female-31-50` highest, `male-50+` lowest) and, if it clicked, also a `book-now-hover` with ~80% probability; a non-clicking session emits a `book-now-hover` with ~30% probability — yielding hovers > clicks, a click-through % ≈ 8–12%, a hover→click funnel % ≈ ~80% (both strictly between 0 and 100). Each event's `createdAt` = midnight-of-its-day (local) + a random offset within that day (today's events capped before "now"). Events inserted with `prisma.event.createMany({ data: […] })` (SQLite + Prisma 6 supports it). Owner #2's venue: **no events**.
- **Canned data location & shape:** `scripts/seed-data/hotel-mizrahi.json` and `scripts/seed-data/the-levant-house.json` — each a JSON object keyed by the 7 `VisitorType` strings → `CopyBundle`. `seed.mjs` reads them with `readFileSync(new URL('./seed-data/<file>.json', import.meta.url), 'utf8')` + `JSON.parse` (bulletproof across Node versions; no import-attribute concerns). A new Vitest test in `apps/owner` validates them.
- **DB connection from the root script:** `seed.mjs` resolves the repo root from `import.meta.url`, `process.loadEnvFile(<repo>/apps/owner/.env)` (wrapped — friendly "run `cp apps/owner/.env.example apps/owner/.env` first" + exit 1 if absent), then constructs `new PrismaClient({ datasources: { db: { url: resolvedUrl } } })` where `resolvedUrl` rewrites a `file:./dev.db` `DATABASE_URL` to an **absolute** path under `apps/owner/prisma/` (mirroring how Prisma resolves SQLite paths relative to `schema.prisma`) so the seed writes the same DB the app reads. If a query throws because tables don't exist, it prints "run `pnpm db:migrate` first" and exits 1. Always `await prisma.$disconnect()` in a `finally`; non-zero exit on any error.

## Scope (files)

**New:**
- `scripts/seed-data/hotel-mizrahi.json` — `{ "neutral": {…CopyBundle…}, "male-18-30": {…}, … }` (7 entries; each `copy.variant` equals its key). Generated once / hand-authored; each bundle passes `validateCopyBundle` and is coherent for "Hotel Mizrahi" (an opulent resort — the canned copy should read naturally with the `mardan-palace` hero image).
- `scripts/seed-data/the-levant-house.json` — same shape, 7 entries, coherent for "The Levant House" (paired with `burj-al-arab`).
- `apps/owner/src/__tests__/seed-data.test.ts` — imports both JSON files; for each of the 14 bundles: asserts `validateCopyBundle(bundle).ok`, asserts `bundle.variant` === its key, asserts `parsePageVariantContent({ schemaVersion: SLOT_SCHEMA_VERSION, copy: bundle }).ok`; asserts each file's key set === `allVisitorVariants()` (exactly the 7, no extras/missing). Pure (no DB) — fits the existing `apps/owner` Vitest setup; catches canned-data drift if the contract changes. (Mirrors #4's "a test asserts coverage" pattern.)

**Rewritten:**
- `scripts/seed.mjs` — the real seed. Plain Node ESM (`node scripts/seed.mjs`, no transpiler — must stay `.mjs`, no TS imports). Structure:
  1. Header comment: what it creates, that re-running resets the two demo owners, the env it needs (`DATABASE_URL` only — not `SESSION_SECRET`/`ANTHROPIC_API_KEY`), and the note about resolving `@prisma/client`/`bcryptjs` via the hoisted `node_modules`.
  2. Constants: the two demo emails/passwords, venue names/slugs, stock-image ids, descriptions, the event-distribution params, the PRNG seed.
  3. `process.loadEnvFile(apps/owner/.env)` (friendly error on miss), resolve absolute `DATABASE_URL`, `import { PrismaClient }`, `import bcrypt from 'bcryptjs'`, instantiate Prisma against the resolved URL.
  4. In a `try`: `deleteMany` the two demo owners by email (reset). Create Owner #1 (`bcrypt.hash(pw, 10)`, back-dated `createdAt`) → its `Venue` ("Hotel Mizrahi" / `hotelmizrahi` / description / `imageKind:'stock'` / `imageValue:'mardan-palace'` / `publishState:'published'` / back-dated `publishedAt`+`slugLockedAt`+`createdAt`) → 7 `PageVariant` rows (loop `allVisitorVariants()` order; `content: { schemaVersion: 1, copy: hotelMizrahiBundles[variant] }`) → generate the simulated sessions and `event.createMany` the ~1,100+ rows with explicit historical `createdAt`s. Then Owner #2 the same way ("The Levant House" / `thelevanthouse` / its bundles / `imageValue:'burj-al-arab'`) but **no events**. `console.log` progress at each step and a final summary (emails, slugs, event count, "sign in at http://localhost:5111").
  5. `catch`: if the message looks like a missing-table error, print "run `pnpm db:migrate` first"; else print the error; `process.exitCode = 1`.
  6. `finally`: `await prisma.$disconnect()`.
- `scripts/` no longer just `seed.mjs` — add the `seed-data/` dir. (`pnpm seed` → `node scripts/seed.mjs` in root `package.json` is unchanged; no new scripts.)

## Out of scope

No schema change → **no Prisma migration, no `apps/owner/prisma/CHANGELOG.md` entry**. **No `@mizrahitality/contracts` change.** **No new dependencies** (the seed uses already-present `@prisma/client` + `bcryptjs` via the hoisted store; no `tsx`, no `dotenv` — Node 22's `process.loadEnvFile` covers env loading). No live Claude API call at seed time (canned JSON). No `Session` rows seeded (the reviewer signs in normally). No production data, no real domains/booking/payments. The seed doesn't run migrations itself (`pnpm db:migrate` is the documented prerequisite, kept that way). No change to the owner app, the customer app, the REST API, or the dashboard/aggregator — #9 only writes rows the existing code reads. Tests still never touch `apps/owner/prisma/dev.db` (Vitest uses its own `vitest-tmp.db` via `globalSetup`); the new test is pure and DB-less.
